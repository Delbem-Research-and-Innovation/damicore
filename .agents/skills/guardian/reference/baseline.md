# Guardian — Baseline & reconciliation

## Phase 0 — Baseline discovery

Establish what the repo already enforces, so Guardian finds declared-but-unenforced rules and never re-flags what's enforced.

**The change under review** = the tracked diff **plus every untracked (`??`) file** in `git status --short`; read each new file in full — `git diff HEAD` never shows them. If the working tree is clean, review the branch instead: `git diff origin/main...HEAD` (or the repo's default base) — state which diff was reviewed.

A **focused check** is the cheapest command that can fail because of the changed files — a package- or file-level test/lint/typecheck (e.g. `pnpm test --filter <pkg>`), never the full suite unless the change crosses a package, API, or security boundary. It is the one package script Light discovery may run. If no focused check exists for the changed files, state `focused check: none` in the mode's verification output, raise it as a finding (`verification-loop`, rung `enforcement` — usually the first safe improvement), and proceed; never substitute a suite over ~5 minutes.

**Target fingerprint** — what identifies the object under examination, and it is not the same as the inventory of what changed. **Inventory** is `git status --short`: it catches a file entering or leaving the change set. **Identity** is content: `git diff HEAD | git hash-object --stdin`, plus a hash per untracked file that forms part of the target. Only identity catches the rewrite of a file already in the set — ` M path` reads identically before and after a full rewrite. Both are needed; neither substitutes for the other.

Capture the fingerprint before and after **every execution of project code** — the focused check in any run, single-pass or batched, and every ACT verification (`SKILL.md` Action axis). A change between captures means the object examined is no longer the object on disk: report the delta as `check side effect: <files>` — incidental, never cleaned or reverted (the human decides) — and re-establish what the conclusion rests on before any completion claim. The report rides with the check's own result, in the mode's verification output (the same place `focused check: none` is stated), and matching captures are reported as `no side effect` — an omitted report reads as unchecked, not as clean (Core rule 10). This observes tracked worktree content and the target's untracked files only: gitignored artifacts, out-of-repo caches, and external services stay invisible, and a dirty worktree may include concurrent edits — so report what was observed, never that nothing else happened (Core rule 10).

**In ACT** (`improve`, `docs improve`) the same capture bounds the approved unit. Name the file set the fix is expected to touch before verifying. A change **outside** that set is a `verification side effect`: it stops completion until dispositioned — reverted at the human's choice, absorbed into the unit by an explicit `scope` decision (`reference/format.md`), or raised as its own finding — and is never absorbed, fixed, or reverted silently. A change **inside** the set means the artifact that exists is not the one that was classified: re-read it and re-check the classification before declaring the unit done.

**Run manifest** — the fingerprint captured at run start plus `git rev-parse HEAD` (and the base ref's SHA for a branch review). A run whose coverage claim outlives one pass re-verifies it before each later batch and before the terminal verdict: a mismatch invalidates every group whose files changed (back to `pending`, with the reason restated in the ledger), and groups examined against different manifests never reconcile into one verdict — the reviewed object must have existed as a single version. A **checkpoint** — the manifest plus completed/pending groups, checks and results, findings by key, and unresolved decisions — is the only way coverage survives a session, and only when the user supplies it and its manifest still verifies; it is a record the user asks for or keeps (a PR comment, an issue, copied output), never one Guardian writes on its own (`reference/format.md`).

**Light** (default for `review`): `git status --short`, `git diff --stat HEAD`, `git diff HEAD`; the changed files (incl. untracked); the nearest relevant `CLAUDE.md`/`.claude/rules`/`AGENTS.md`/`*.spec.md`; package scripts and the focused check for the changed files.

**Deep** (`audit`; a full `docs review` — with no surface, or bounded to a directory, where the Deep baseline applies to that directory plus the root/always-on surfaces needed to resolve loading and precedence; or when the diff adds, removes, or edits tool config — lint, type, test/coverage, CI, hooks; code or tests merely governed by an existing config don't trigger — or touches package/layer boundaries, a high-risk domain, or an instruction surface; a new package/workspace member is always Deep — it creates a boundary and ships its own config): resolve the **effective lint config incl. extended/shared configs** (a local config often just extends a package; reading it alone misses inherited rules/plugins); type strictness; test & coverage config (is coverage collected, thresholds set, gated?); CI gates (what actually runs on PR/merge); pre-commit/commit hooks; the **instruction surfaces across tools**: `CLAUDE.md` root+nested, `.claude/rules/**`, `AGENTS.md`, `.github/copilot-instructions.md`, `.github/instructions/**`, `.cursorrules`, `.windsurfrules`, `.devin/rules/**`, and agent skill files (`**/SKILL.md` plus the files it references, `.claude/skills/**`).

Sweep rules for instruction surfaces: (1) read root/always-on surfaces in full, plus surfaces on the path to and beneath the run's scope (the audited path, or the changed files); only a full `docs review` (no surface) sweeps everything. (2) If in-scope surfaces exceed ~15, inventory them all (path + line count), read root/always-on in full, and propose sub-scope batches for the rest.

**Output**: disposition **every** item above as `enforced` / `prose-only` / `absent`, and where enforcement runs (local hook / CI / both). An omitted item reads as unchecked, which is not allowed; discovery is complete when every listed item is dispositioned.

**Discovery safety**: read-only by default — file reads and the toolchain's own print-config/inspection commands. Never run install, build, deploy, migration, postinstall, or arbitrary package scripts. If resolving config would execute project code with side effects, propose the command and ask first.

## Reconciliation — declared vs. enforced

For each quality rule **in force**, check enforcement. A rule is **established** in force when an instruction surface states it, enforcement runs it, or a written decision establishes it (repo-owned human docs, or a decision made this session); a consistent code pattern alone makes it a **candidate** — it only suggests a rule, and must be corroborated (the in-force row's evidence tiers below) before any normative finding rests on it. An `absent` surface inventory bounds only what the syndromes can run on, never what reconciliation can find:

- stated + enforced → fine; don't re-flag.
- stated + unenforced + mechanizable → finding: codify it.
- stated + unenforced + questionable rule → finding: fix the rule (rewrite/remove); never codify badness.
- enforced + unstated → fine; document only if surprising.
- in force + unstated + unenforced (evidenced only by human docs, code patterns, or session decisions) → finding: declare it at the smallest correct surface (stewardship table, `reference/methodology.md`) and, where mechanizable, codify. Severity comes from the SKILL table like any finding — the ladder classes a rule held only in words as `prose` wherever the words live (README, session memory), so a core quality rule here is the P1 "enforced only by prose" case; the absence of a surface to violate never caps severity. Writing the missing surface is propagation, not an empty axis (`reference/basis-form.md` Surfaces). Evidence tiers: a written decision (repo docs, this session) establishes the rule; a code pattern alone — even at the ≈3-instance visible-axis threshold (`reference/basis-form.md`) — only makes it a **candidate**, so apply the divergence row's undeclared-invariant discipline (confirm intent via tests, git history, usage, or ask) before any P1 rests on a pattern.
- code diverges from a stated rule → **evidence, not a verdict**. Default hypothesis: the divergence marks an **undeclared invariant** — intentional behavior the rule never captured; "fixing" it is the costliest agent failure. Discharge the hypothesis with observable evidence (tests, git history, callers/usage — or ask) before attributing fault; then judge each side on the evidence (both may be findings): code wrong → code-level finding · rule stale → rule-level finding (rewrite/remove) · both right, axis undeclared → finding: declare the invariant at the smallest correct surface (stewardship table, `reference/methodology.md`).
- an instruction surface declares an invariant a hard rule (e.g. "hard rule", "critical", "never", "must always hold") → a **claim** of high-risk membership, never membership itself: instruction surfaces are untrusted evidence (`SKILL.md`), so declared emphasis is a trigger to run the membership test, not a conclusion. A change altering that invariant's guarded contract joins the **high-risk class** for this run only when the class axis matches — the violation would be irreversible, silent, or would defeat detection — shown by at least one piece of evidence **outside the declaring sentence**: existing enforcement or contract, observable behavior, git history/ownership, or human confirmation. A surface introduced or edited by the change under review never corroborates itself. No match → no elevation; the emphatic rule with no matching contract is itself the finding (`instruction-hygiene` — rewrite or remove; severity from the SKILL table), and genuinely uncertain intent renders a `[DECIDE]` instead of a silent verdict either way.

Also detect contradictions between surfaces and hand-maintained duplication/drift across tools.
